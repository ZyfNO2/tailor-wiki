# Tailor Wiki 总需求与协作开发约定

协作需求草案 · 2026-10-27。本文汇总用户已确认需求、当前工程事实与待讨论提案，作为共同开发的需求入口。写入本文不等于新增功能已实现，也不等于批准所有提案实施。普通实现细节由开发者在已授权范围内决定，不要求逐项冻结 SPEC。

## 1. 产品目标

基于 DSH Paper Tailor 的独立科研技能包。让 Agent 接着用户已有论文、笔记、代码和实验推进：整理知识、寻找可验证的改进方向、组合方法、规划实验、分析结果、组织研究故事，并持续维护 Wiki。

核心主旨：围绕研究目标抽取相关、可比较的实验数据，再讲清楚“为什么做、遇到了什么问题、怎样解决、证据支持什么”。筛选按研究目标和比较条件，不按结果是否支持预期；保留相关负结果与不确定性。没有实验也可以先形成待验证的设计故事。

技能包先更新，DSH 插件随后独立适配、验收和发布。各宿主能力不能由文件存在推定。项目灵感包含 ASu-skills 将已有材料转为有依据、可接续的交付方式；不机械移植求职流程。

## 2. 工作台职责：给人看（用户再次明确）

**工作台只负责方便人阅读 Wiki、理解实验编排和查看研究进展。它是展示层，不是研究执行或调度中心。**

展示可以交互：搜索、筛选、展开来源、查看版本差异、画布缩放平移、定位上下游任务、比较结果、跳转文件。交互用于理解已有内容，不用于改变真实实验或研究决定。

| 工作台负责 | 工作台不负责 |
| --- | --- |
| 展示 Wiki 正文、来源、关联与问题 | 生成或裁决研究事实 |
| 把已有实验计划、任务依赖和状态显示清楚 | 创建执行规则、调度实验或驱动 Agent |
| 阅读方案、Run、结果、审查和故事 | 通过按钮启动/暂停/重试训练、批准实验 |
| 展示已有成员、任务和产物；无成员时为空或占位 | 创建 Team、派发任务、伪造成员活动 |
| 显示源文件版本、读取时间、错误和缺失 | 在浏览器维护另一套权威进度或结果 |

研究操作由 Agent 与实际工具完成，依据文件和 trace 恢复；审批发生在用户与 Agent 的交互中，不要求工作台增加审批流程。DAG 布局移动仅影响展示，不改变任务依赖。知识图谱表达知识关系，DAG 表达任务依赖，二者分开。

本次职责澄清以本文为准，不更新 README，也不要求 UI 协作者实现执行控制台。

## 4. 使用方式与软依赖

| 入口意图 | 实际 Skill | 目标与产物 | 推荐交接 |
| --- | --- | --- | --- |
| /init | wiki-maintain | 全量盘点指定范围，整理或恢复 Wiki | 可供裁缝使用，也可单独维护 |
| /tailor | academic-tailor | 方法组合、来源、兼容性/资源核验、TAILOR.md 与任务 DAG | 实验设计或直接讲设计故事 |
| /exp | experiment-design | 对照、消融、预算、判据、EXPERIMENT-PLAN.md；分析已有结果 | 故事与 Wiki 回流 |
| /story | research-story | 简版故事、贡献证据、局限与 STORY-PLAN.md | Wiki 回流；必要补证建议 |

无材料时询问研究目标与是否需要联网寻找资料；已有明确答复不重复问。短名称是意图约定，不能覆盖宿主内置 /init；完整 Skill 名继续有效。

软依赖不是忽略真实前置：缺数据或接口只阻塞依赖它的实验，不阻塞可以先完成的方案和叙事。独立使用不会自动执行所有阶段；实验与故事收尾的 Wiki 维护是已确认例外。

## 5. 各模块要求

### R-WIKI：知识整理与维护

- 默认覆盖用户指定范围，登记逐文件读取、未变复用、部分读取、失败/不支持与排除原因；不擅自抽样后称全量完成。
- 正文自然可读，证据记录单独展开。原文定位绑定来源版本；引用存在不等于支持结论。
- 设计、报告、本轮实际结果、模拟与假设区分；冲突按对象、条件和版本处理，不能以最新日期替代事实判断。
- 增量只更新变化来源和受影响页面；保持身份、历史、人工内容。未变化应无内容漂移，失败可恢复。
- 实验和故事产物落盘后默认回流；保存待同步状态，重试维护不重跑实验，不把 Wiki 输出循环摄入。

### R-TAILOR：方法与创新假设

- 从目标及真实材料提出少量有依据的候选与推荐，不为凑 A+b+c 堆模块。
- 说明问题依据、模块出处、接入位置与影响最终输出的机制；概念兼容、接口核验、样本跑通分别记录。
- 可设计、可试跑、可完整执行与用户选择状态分开。资源估算不当实测，读报告不当复现。
- 方案输出研究任务 DAG；任务 ID 稳定，节点所属实验与执行前置分开，禁止自依赖与伪边。允许合法独立节点。

### R-EXP：实验设计、结果与记录

- 一个实验对应明确问题；记录基线、对照、划分、配置、指标定义/聚合、预算、保护指标与停止条件。
- 计划、任务、Run、审查决定分别记录；保存全部尝试与失败，缺指标不填 0。
- 输入、实现、执行、结果比较依赖分别表达；正式评价前明确协议，已有证据可复用，不无谓重跑。
- 默认设计/分析已有结果；真实执行遵守已有用户授权。是否有执行能力以环境和实际工具为准。
- 结果筛选按目标和可比性，关联原始证据，不能只选最佳 Run 或把模拟写成实测。

### R-STORY：讲清楚研究

- 开头约 150–300 字或四个短段，先回答为什么做、具体问题、怎样解决、数据支持什么/还需验证什么。
- 一条清楚主线优先；证据表、内部编号、详细风险与图表计划后置，不重复审计式免责声明。
- 有数据时讲证据范围内的故事；只有设计时讲待验证叙事。探索性解释不伪装为事前假设。
- 新颖性、性能与机制解释分别判断；不直接改用户论文正文，论文写入仍先提议并确认。

### R-VIEW：工作台展示与默认入口

- 任一流程完成或部分完成且有产物，就提供该工作区可用的展示入口；已有服务先核对绑定工作区。
- 无 Wiki 但有裁缝/实验/故事时仍可展示；缺少其他产物显示空状态，不强制补跑流程。
- 展示区域：项目概览、Wiki 与来源、知识图谱、裁缝方案、DAG、实验计划与结果、故事、任务与 Team 占位。
- 展示范围以实际文件为准；未实现图谱/Team 不伪造关系或成员。新 UI 可重新设计布局，无需照搬旧原型。
- 启动/构建/读取失败时说明原因并给 Markdown 入口，不返回不可访问链接。静态快照与持续读取服务需明确区分。
- 所有展示能力受第 2 节职责约束。

## 6. /auto-research：轻量总路由

用户希望一键让 Agent 整理资料、寻找 idea、推进裁缝、实验和故事；写给 Agent 的使用总览即可，不引入强制状态机或复杂新框架。

建议语义：读取当前进度后自主选择下一步，跳过已完成工作；材料不足时补必要资料。有实验先核对和分析，继续到研究主线、贡献定位等需要主观取舍的位置再集中讨论，而不是每一步都询问。

默认联网获取公开来源，常规研究及成本明确的小检查自主推进；重大分支按用户代选授权处理，未具体授权的高风险实验、付费、覆盖或发布先确认。没有工具或关键输入时不假称已跑。论文正文、对外发布等原有授权边界不因自动入口消失。

沿用五个专业 Skill、文件和 trace，默认 Wiki 回流与展示交付；额外分发 auto-research 路由 Skill，不新增执行引擎或总状态库。

参考 [ASu-skills](https://github.com/Hisn00w/ASu-skills) 的独立入口、目标对齐、事实表达和交接方式；拟类比的研究导学、实验复盘、答辩追问已按后续授权纳入，auto-research 已按后续授权实施，行为验收与源码测试分开记录。

## 7. 协作接口与事实来源

不提前冻结一套新数据库或大 JSON Schema。沿用已有文件，协作者按下表协商必要读取字段；缺字段显示未知，解析失败保留错误。

| 对象 | 权威材料 | 协作时需保留 |
| --- | --- | --- |
| 知识与引用 | Wiki 已发布快照/来源记录 | page/source 身份、版本、正文、引用、问题与复核范围 |
| 方案 | TAILOR.md | 方案身份、基线/模块、来源、假设、决策、就绪与缺口 |
| 任务依赖 | 既有 DAG 或 RESEARCH-DAG.md | task ID、输入/输出、前置条件、状态、关联方案 |
| 实验计划 | EXPERIMENT-PLAN.md | experiment ID、协议、预算、判据、任务映射 |
| 实验运行/审查 | Run 文件、日志、指标、审查记录 | run ID、计划版本、实际状态、原始结果与判断 |
| 叙事 | STORY-PLAN.md | 主线、主张、依据、未知与关联对象 |
| 维护状态 | 现有 trace/journal/feedback 记录 | 实际操作、版本、失败、恢复点与待同步 |

一个计划可有多个 Run；文件 hash 不是实验身份。工作台和 Markdown 汇总可以投影同一事实，不能变成各自独立可写的状态源。产物出现后核对关联任务，文档完成不推导科研完成。

协作纪律：改前读当前内容，不覆盖他人未提交修改；多人涉及同一文件先明确负责范围。没有新变更不重复验证，无依据不写通过。不主动 push；对外使用固定技能包名称，内部以 Git 提交和校验清单追溯。

bug 最少记录：环境/提交、步骤或输入、期望与实际、首错/截图、涉及文件、修复及验证。不能把跨文件任务状态问题仅归给 UI。需求调整在本文追加简短变更记录，避免聊天和实现各说一套。

## 10. 联合验收场景

1. 仅给资料：Wiki 有正文、来源、覆盖记录；图文未读和失败真实显示。
2. 仅给方案：无需先做 Wiki，能出裁缝/DAG 并查看产物；无自依赖，任务与产物一致。
3. 仅给实验结果：核对可比性，保留负结果与全部尝试，形成简版故事，再增量维护 Wiki。
4. 只有研究设计：可提前讲故事，明确未验证，不生成实验成绩。
5. 维护与恢复：变化仅影响相关页；重复无漂移；失败保留待同步，只重试维护。
6. 单阶段工作台：五种独立入口（含导学）分别可查看产物，缺阶段为空；读取错误不伪装无数据。
7. 完整展示：方案→任务→实验→Run→故事可定位，来源版本、陈旧状态与未解决问题可见。
8. 只读边界：浏览、筛选和画布操作不改变研究文件、不启动任务；Team 占位不显示伪造运行。
9. 自动入口（实施后）：已有成果不重跑；实验前按用户授权处理；缺输入不伪造完成，收尾有真实产物/维护/展示状态。

以上是验收要求，不是当前已通过清单。工程 fixture、真实模型产物、真实实验结果分别报告。
